# Database migrations

SimpleWay Drawing treats database migrations as immutable release artifacts.

## Foundation baseline

`packages/database/migrations/0000_foundation_alpha.sql` is the canonical pre-production baseline for the Foundation Alpha schema. It was frozen from a migration generated by Drizzle and validated against PostgreSQL 16 in CI before the first persistent production database.

The baseline must not be edited after it has been applied to any persistent environment.

## Applying migrations

Use:

```bash
pnpm db:migrate
```

The versioned runner:

1. creates `swd_schema_migrations` when necessary;
2. reads ordered `*.sql` files from `packages/database/migrations`;
3. calculates SHA-256 for every migration;
4. applies unapplied migrations transactionally;
5. records name, checksum and application timestamp;
6. refuses to continue if an already-applied migration has a different checksum.

Running the command repeatedly is safe. Applied migrations are skipped after checksum verification.

## Adding a schema change after production starts

Never modify an applied migration. Create a new ordered file instead:

```text
0001_<change>.sql
0002_<change>.sql
...
```

Every migration must be forward-only, reviewable, transactional where PostgreSQL permits it, and validated on a clean PostgreSQL service in CI.

For destructive changes use an expand/migrate/contract sequence rather than deleting or renaming live columns in one release.

## CI discipline

Before the first persistent deployment, CI generates a diagnostic Drizzle baseline and compares it with `0000_foundation_alpha.sql`. This prevents unnoticed schema drift while the baseline is being frozen.

CI then applies the versioned migration runner twice. The first execution must apply the migration and the second must skip it, proving idempotency. Database verification checks both application tables and the migration registry.

After the first persistent production deployment, `0000_foundation_alpha.sql` becomes permanently immutable. Future schema changes must be expressed only as incremental migrations.

## Production deployment order

1. back up or snapshot the database when applicable;
2. run `pnpm db:migrate` using the production `DATABASE_URL`;
3. require a successful migration result before application promotion;
4. verify `/api/ready`;
5. run remote smoke tests;
6. promote the application deployment.

Do not run `drizzle-kit push` against production.
